# Пользователи, группы и доступ

## Модель
UID определяет пользователя, GID — группу. Есть основная и дополнительные группы.
Имя ops само по себе не выдаёт административных прав.
id показывает членство, но не заменяет проверку доступа к объекту.

Права владельца, группы и остальных — разные классы. Для каталога r позволяет
читать список имён, x — проходить к объектам, w вместе с x — создавать и удалять
записи. Права файла проверяются отдельно.

## Режим 2750
2 — setgid: новые объекты наследуют группу каталога.
7 — rwx владельцу, 5 — r-x группе, 0 — ничего остальным.
Setgid не гарантирует запись группы в новые файлы: режим зависит от создания и umask.
В моей практике /srv/team принадлежит dev:lab, а view вне lab и без доступа.
Я показал режим каталога, но не отдельный вывод владельца и режима probe.

## sudo и оператор
sudo выполняет разрешённое политикой действие от другой учётной записи.
sudo -u в моих проверках запускал команду от dev или view, а не выдавал им sudo.
Полномочия ops ещё предстоит определить по командам, аргументам и службам.
Право менять unit, код или конфиг привилегированной службы тоже может расширять доступ.

## Команды по темам и классам
| Тема | Класс | Использовано |
|---|---|---|
| Учётные записи | Просмотр | getent passwd, getent group, id |
| Группы | Изменение | usermod -aG lab dev |
| Каталог | Изменение | mkdir /srv/team; chown dev:lab /srv/team; chmod 2750 /srv/team |
| Доступ | Проба с изменением при успехе | sudo -u dev touch /srv/team/probe; sudo -u view touch /srv/team/blocked |
| Доступ | Просмотр | sudo -u view ls /srv/team; ls -ld /srv/team |

Это исторические команды, не инструкция повторно создавать объекты.
Первичные локальные справочники: man id, man chmod, man usermod, man sudoers.

[usermod(8): дополнительные группы и -aG](https://man7.org/linux/man-pages/man8/usermod.8.html).
Версию и доступные параметры сверяю с man на своей Ubuntu.
