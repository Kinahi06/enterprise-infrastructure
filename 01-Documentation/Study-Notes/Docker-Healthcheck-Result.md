# Простой HTTP healthcheck - результат

16.10.2026. Практика с опорой на объяснение и готовые команды.

## Показано

- Скриншот 18:32: прямой wget в оболочке VM linux01 из ~/compose-pair, exit: 4. Проверялся порт 80 VM. Для GNU Wget это сетевой сбой; подробная причина из-за -q не видна и не установлена.
- Скриншот 18:35: фрагмент config с web training-site:v2, proxy nginx:1.30.5-alpine, публикацией proxy на 127.0.0.1:8138 и read_only bind proxy.conf. Созданы сеть и контейнеры, оба Up.
- Выполнен sudo docker compose exec web wget -q -T 2 -O /dev/null http://127.0.0.1/, затем echo $?; показан 0. Точный HTTP-код, v2 и доступ через proxy отдельно не подтверждены этим запросом.

## Сообщено

После инструкции добавить простой CMD-healthcheck к web (interval 5s, timeout 3s, retries 3), выполнить config/up/ps и ожидать Up (healthy) ученик ответил: «да, все как ты и сказал». Результат healthy фиксируется по сообщению; итоговый YAML и ps не показаны. Сохранение копии YAML, переходы starting/unhealthy и down после блока отдельно не подтверждены.

## Понимание и помощь

Объяснены wget, -q/-T/-O, exit status против HTTP-кода, область localhost, CMD-список и ключи healthcheck. После ошибки прямого запроса наставник указал место выполнения и дал exec web. Ученик верно назвал изменение -T 2 на -T 1. Ответ о работе контейнера и его внутреннего IP потребовал уточнения: проверен HTTP на loopback, а не адрес в сети Compose и не весь путь через proxy. Новый самостоятельный ответ после уточнения пока не получен.

## Решение и продолжение

Простой блок пройден с помощью по сообщению ученика. Это не независимый диагностический зачёт и не завершение Docker; числовые уровни не повышаются. Далее объяснить service_started против service_healthy, затем отдельная практика ожидания готовности при запуске. Unhealthy сам по себе не перезапускает контейнер и не останавливает работающий proxy. Расширенный опыт с /tmp/lab-unhealthy остаётся отложенным.

Изменения VM выполнял ученик; преподаватель только объяснял и обновлял документацию.
