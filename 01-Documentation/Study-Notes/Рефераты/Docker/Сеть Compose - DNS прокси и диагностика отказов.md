# Сеть Docker Compose
## DNS, прокси и диагностика отказов
Практика 15-16 октября 2026 года. Пишу от своего лица; учился с подсказками, оформление выполнено с помощью ИИ. Показанные результаты отделяю от сообщений и объяснений наставника.

### 1. Зачем я связал два сервиса
В /home/linux01/compose-pair я описал проект lab-compose-pair. Сервис web использовал мой образ training-site:v2, сервис proxy - nginx:1.30.5-alpine. Запрос проходил так:
```text
VM 127.0.0.1:8138 -> proxy:80 -> web:80
```
Compose создал общую сеть lab-compose-pair_default. В ней имя службы web разрешается в адрес её контейнера. Это внутреннее имя, а не средство выхода в интернет. На скриншоте wget определил web как 172.18.0.2; этот IP - наблюдение конкретного запуска, его не следует фиксировать в конфигурации.
У proxy был опубликован порт 127.0.0.1:8138:80. У web публикации на хост не было: для связи контейнеров в общей сети она не требуется. Показанное в ps значение 80/tcp само по себе не означает публикацию порта на VM.

### Адрес зависит от того, откуда я обращаюсь
- На VM адрес 127.0.0.1:8138 ведёт к опубликованному порту proxy.
- Внутри proxy адрес web:80 ведёт к соседнему контейнеру сайта.
- Внутри proxy адрес localhost:80 ведёт к самому proxy, а не к web.

### 2. Настройка прокси
Исправленная конфигурация proxy.conf:
```nginx
server {
    listen 80;
    location / {
        proxy_pass http://web:80;
    }
}
```
Файл хоста подключался к /etc/nginx/conf.d/default.conf с ro. Относительный путь ./proxy.conf относится к папке проекта. Короткий depends_on: [web] задаёт порядок запуска, но не проверяет готовность HTTP.
Источники: https://docs.docker.com/compose/how-tos/networking/
https://docs.docker.com/compose/how-tos/startup-order/

# Где потерялся ответ
## Как я разделил цепочку на участки

### 3. Контейнеры Up, но curl ждёт
Я показал два работающих контейнера и публикацию proxy на 8138. HTTP-запрос с VM завершался curl (28): за пять секунд не получено ни байта. Статус Up подтверждал работающие процессы, но не исправность маршрута запроса.
По инструкции наставника я проверил два участка отдельно:
```bash
curl -v --noproxy '*' --max-time 5 http://127.0.0.1:8138/
sudo docker compose exec proxy wget -T 5 -S -O - http://web/
cat proxy.conf
sudo docker compose logs --tail 20 proxy web
```
Здесь новые применения команд, уже знакомых по предыдущим блокам:
- curl -v показал Connected и отправленный GET: TCP-соединение с портом хоста установилось. --noproxy '*' исключил использование клиентского HTTP-прокси.
- compose exec proxy запустил wget внутри службы proxy. -T 5 ограничил ожидание, -S показал заголовки, -O - направил тело в терминал.
- Внутренний запрос вернул HTTP 200 и Image version 2. Имя web разрешалось, сайт отвечал: связь между контейнерами работала.
- Журнал web содержал GET от контейнера proxy с кодом 200. В журнале proxy были записи 499, соответствующие прерыванию клиентом ожидания; это не доказательство причины задержки upstream.

### 4. Ошибка в адресе назначения
В файле я написал proxy_pass http://80; вместо http://web:80;. Число 80 без предшествующего имени и двоеточия стояло на месте адреса назначения. Ошибку указал наставник по скриншоту конфигурации; самостоятельно причину я не определил.
Для применения исправленного подключённого файла наставник предложил:
```bash
sudo docker compose up -d --no-deps --force-recreate proxy
```
--no-deps выбирает запуск без зависимостей, --force-recreate принудительно пересоздаёт выбранную службу. Отдельный вывод выполнения этой команды не показан; после исправления я сообщил HTTP 200 через порт 8138.
Источник: https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass

# Отказ одного сервиса
## Что показал опыт и почему я его повторил

### 5. Остановленный сайт при работающем прокси
Сначала я удалил проект через down до проверки отказа только web. Это не показывало поведение живого proxy без доступного сайта. Поэтому стенд был поднят снова для отдельного опыта с stop web и последующим start web.
На итоговом скриншоте 16 октября показано:
- После stop web контейнер сайта имел Exited (0), а proxy оставался Up с публикацией 8138.
- Запрос с --max-time 5 завершился curl (28) через 5004 ms, 0 bytes received. HTTP-код от прокси не получен.
- После start web запрос через proxy вернул HTTP 200 и тело <h1>Image version 2</h1>.
- После down оба контейнера и сеть lab-compose-pair_default показаны как Removed.
Главная цель - увидеть зависимость работающего прокси от сайта за ним и восстановление ответа после возврата backend. Ещё один stop/start для подтверждения того же результата не нужен.

### Почему обещанный 502 не появился
Наставник слишком уверенно задал HTTP 502 как обязательный результат за пять секунд. Это ожидание было исправлено по фактическому выводу. Предел curl относится ко всему запросу; Nginx может ждать соединения с upstream дольше, стандартный proxy_connect_timeout равен 60 секундам. Точный этап ожидания при остановленном web отдельно не исследовался. Нельзя записывать полученный curl (28) как HTTP 502 или утверждать, какой HTTP-код появился бы позднее.

### Мой итог и следующий шаг
Практическая часть завершена с помощью. На вопрос о web вместо localhost я ответил, что не знаю, предположил связь с выходом в интернет. Наставник объяснил внутренний DNS и отдельный localhost контейнеров; самостоятельный ответ после объяснения пока не показан. Числовые уровни самостоятельности не повышаю.
Ответы о сохранении YAML и различии stop/down в предыдущем блоке уже даны по сути верно, с уточнением терминов. Старый реферат Dockerfile/Compose отражает состояние до этих ответов; актуальная отметка находится здесь и в прогрессе.
Следующее задание - healthcheck и зависимость service_healthy. Оно выдано, но ещё не выполнено. Практику Healthcheck в этот завершённый опыт не включаю.
