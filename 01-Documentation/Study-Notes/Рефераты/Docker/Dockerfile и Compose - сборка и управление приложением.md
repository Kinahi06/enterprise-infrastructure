### 1. Как я получил собственный образ
В /home/linux01/image-site я работал с index.html и Dockerfile. Базовый образ - nginx:1.30.5-alpine. Учебная инструкция сборки:
```dockerfile
FROM nginx:1.30.5-alpine
COPY index.html /usr/share/nginx/html/index.html
```
FROM задаёт базовый образ, COPY помещает файл в образ во время сборки. Это не постоянная связь с файлом хоста. Уже знакомые команды запуска и HTTP-проверки здесь повторно не разбираю.
Новая команда сборки:
```bash
sudo docker build -t training-site:v1 .
```
- -t задаёт имя и тег образа; точка выбирает текущий каталог как контекст сборки.
- Контекст - доступные сборщику файлы, из которых COPY берёт исходник.
- Тег помогает выбрать образ. Переназначение тега не переводит существующий контейнер на другой образ.

### Что произошло в опыте v1/v2
- Сборка v1 завершилась успешно по моему сообщению. Первый HTTP-код я не указал в отчёте.
- Изменение исходного index.html не изменило страницу работающего image-web-v1.
- После сборки training-site:v2 старый контейнер по-прежнему показывал прежнюю страницу.
- Новый image-web-v2 показал изменения. Остановку обоих учебных контейнеров я подтвердил сообщением.
Мне объяснили: при bind mount контейнер читает файл хоста, а COPY фиксирует содержимое при сборке. Stop/start запускает тот же контейнер с прежним образом; опыт stop/start после сборки v2 отдельно не показан.
Источник: https://docs.docker.com/reference/dockerfile/#copy

# Первый проект Compose
## От команды запуска к описанию приложения

### 2. Установка подходящего пакета
Docker ответил unknown command: docker compose. Проверка apt-cache policy показала установленный docker.io из Ubuntu 24.04, а не docker-ce. Пакет docker-compose-plugin в подключённых репозиториях не найден. Для моей установки выбрали docker-compose-v2:
```bash
sudo apt update && sudo apt install docker-compose-v2
sudo docker compose version
```
На скриншоте показана версия 2.40.3+ds1-0ubuntu1~24.04.1, архитектура пакета arm64. Уведомление о новом ядре - отдельный результат проверки системы после установки; оно не доказывает, что ядро установлено именно этой командой. Перезагрузку в этом блоке я не подтверждал.

### 3. Файл compose.yaml
В задании использовались каталог /home/linux01/compose-site и проект lab-compose-site. Конфигурация для уже собранного локального образа:
```yaml
name: lab-compose-site
services:
  web:
    image: training-site:v2
    pull_policy: never
    ports:
      - "127.0.0.1:8136:80"
```
- services содержит службы приложения, web - имя службы, image - выбранный образ.
- pull_policy: never требует локальный образ; при его отсутствии будет ошибка.
- ports публикует порт 80 контейнера только на loopback хоста, сначала как 8136.
- Отступы YAML делаются пробелами; в этом примере два пробела на уровень.
Compose читает описание приложения при выполнении команды. Само сохранение YAML не перестраивает уже запущенные ресурсы.
Источник установки: https://packages.ubuntu.com/noble/arm64/docker-compose-v2
Модель Compose: https://docs.docker.com/compose/intro/compose-application-model/

# Применение изменений
## Что я проверил и что осталось объяснить

### 4. Новые команды Compose
Команды выполнялись по заданию из папки с compose.yaml:
```bash
sudo docker compose config
sudo docker compose up -d
sudo docker compose ps
sudo docker compose logs --tail 10 web
sudo docker compose ps -q web
sudo docker compose down
sudo docker compose ps -a
```
- config проверяет и выводит итоговую конфигурацию; up -d создаёт или обновляет контейнеры и запускает их в фоне.
- ps показывает контейнеры проекта; -q web выводит ID контейнера службы web. Logs показывает её журнал.
- down останавливает и удаляет контейнеры и обычные сети проекта. Образы и именованные volumes по умолчанию сохраняются. Stop только останавливает контейнеры, оставляя их для последующего запуска.

### Мой итоговый отчёт 15 октября
- Первый запрос: HTTP 200 и страница v2.
- После сохранения YAML с портом 8137 прежний порт 8136 ещё работал.
- После up новый порт заработал, ID контейнера изменился. Это пересоздание, а не только перезапуск того же контейнера.
- Повторный up без правок оставил прежний ID.
- После down список контейнеров проекта стал пустым.
Эти результаты я сообщил в чате; отдельного вывода HTTP, точных ID и списка после down нет. Отказ старого порта после up и наличие GET в логах в итоговом сообщении отдельно не указаны. Установку и версию Compose видно на скриншоте. Новый аудит VM наставником не выполнялся.

### Статус и следующий шаг
Практическая часть выполнена с подсказками. Самостоятельные ответы о сохранении YAML и различии down/stop пока не получены; числовые уровни не повышаю. Следующий практический этап - несколько сервисов и общение по имени службы в сети Compose, после короткой защиты текущего опыта.
