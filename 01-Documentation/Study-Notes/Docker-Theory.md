## Образ, контейнер и виртуальная машина

**Образ (image)** — шаблон файлов приложения и настроек его запуска.
Скачанный образ сам ничего не обслуживает.

**Контейнер (container)** — экземпляр, созданный из образа: настройки,
собственный записываемый слой и запускаемый процесс. Контейнер может быть
остановлен: объект остаётся, хотя процесс уже не работает. Один образ можно
использовать для нескольких контейнеров.

**VM** имеет своё ядро ОС. Linux-контейнеры используют ядро Linux-хоста:
в нашей лаборатории этим хостом будет Ubuntu VM, а не macOS. Контейнер не
является маленькой VM. Изоляция процессов не равна абсолютной безопасности.

[Подробнее: Docker — What is a container?](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/)

## Кто принимает команды

`docker` — клиент. Он обращается к Docker Engine, который управляет образами,
контейнерами и сетями. Поэтому установленный CLI ещё не доказывает доступность
Engine. `docker version` показывает Client и, при успешном подключении, Server.

Ошибка доступа к Docker socket не означает, что Docker отсутствует.
Не исправляй её через `chmod 666` сокета. Группа `docker` фактически даёт
root-уровень возможностей: добавление пользователя — решение о доверии,
а не косметическое отключение sudo. В учебной VM можно использовать sudo
для отдельных Docker-команд, предварительно разобрав сообщение ошибки.

[Подробнее: Docker — Linux post-installation](https://docs.docker.com/engine/install/linux-postinstall/)

## Мини-словарь команд

Шаблоны, а не готовое решение тикета. `<...>` означает твой аргумент.

| Формула | Что делает |
|---|---|
| `docker version` | Проверяет версии клиента и доступного Engine |
| `docker image ls` | Показывает локальные образы |
| `docker pull <образ:тег>` | Скачивает образ; приложение ещё не запущено |
| `docker run <параметры> <образ:тег>` | Создаёт и запускает новый контейнер |
| `docker ps` / `docker ps -a` | Показывает работающие / все контейнеры |
| `docker logs <имя>` | Показывает stdout/stderr контейнера |
| `docker inspect <имя>` | Показывает подробности конфигурации и состояния |
| `docker port <имя>` | Показывает опубликованные порты |
| `docker stop <имя>` | Останавливает процесс контейнера |
| `docker start <имя>` | Запускает существующий остановленный контейнер |

Полезные параметры `run`: `--name <имя>` — понятное имя, `-d` — фоновый запуск.
Повторный `run` не равен `start`: он пытается создать новый объект и может
получить конфликт имени. Удаление контейнера — отдельная операция; сейчас она
не нужна. Данные записываемого слоя не переживают удаление контейнера;
volumes изучим отдельно.

## Порт хоста и порт контейнера

В обычной bridge-сети контейнер имеет собственное сетевое окружение.
`127.0.0.1` внутри него относится к нему, а не к Ubuntu-хосту.

Публикация задаётся при создании:

```text
-p <IP_хоста>:<порт_хоста>:<порт_контейнера>
```

Клиент на Ubuntu обращается к порту хоста; Docker перенаправляет запрос к
порту приложения внутри контейнера. В этой практике IP хоста — `127.0.0.1`:
не публикуем сервис на всех интерфейсах. Если IP опустить, публикация по
умолчанию затронет все интерфейсы. Не открывай firewall ради упражнения.

Запись `80/tcp` в выводе Docker сама по себе ещё не означает публикацию
на хосте. И `EXPOSE` в образе — не замена `-p`.

[Подробнее: Docker — Publishing ports](https://docs.docker.com/get-started/docker-concepts/running-containers/publishing-ports/)

## Знакомая диагностика, новый инструмент

Ты уже умеешь различать процесс, порт и HTTP. Здесь принцип тот же:

1. `ps -a`: контейнер существует? Работает или завершился?
2. `logs`: что сообщает приложение?
3. `port` / `inspect`: куда опубликован порт?
4. `curl`: что получил настоящий клиент?

`Up` не доказывает нужный HTTP-ответ. А `ss` на хосте не всегда показывает
Docker-публикацию отдельным процессом-listener: она может работать через NAT.
Поэтому сопоставляй Docker-конфигурацию и запрос клиента, не только `ss`.
