# Linux: диагностика сервиса

Версия: 23 сентября 2026
Назначение: короткая рабочая шпаргалка по systemd, процессам, socket, HTTP,
правам и файловым системам.

## 1. Золотой маршрут

```text
симптом
  -> systemd status
  -> journal
  -> process / identity
  -> socket / PID
  -> HTTP из нужной точки
  -> config / permissions / filesystem
  -> минимальное изменение
  -> повторная проверка всей цепочки
```

Правило: **одна команда — один вопрос**. Не меняй систему, пока результат
read-only проверки не различает хотя бы две гипотезы.

## 2. Первые пять вопросов

| Вопрос | Формула команды | Ключевые поля | State change |
|---|---|---|---|
| Что видит systemd? | `systemctl status <unit>` | `Loaded`, `Active`, `Main PID` | Нет |
| Почему процесс вышел? | `journalctl -u <unit> -n <N> --no-pager` | errno, path, PID, timestamp | Нет |
| Кто слушает порт? | `ss -lntp 'sport = :<port>'` | local address, PID, process | Нет |
| Отвечает ли HTTP? | `curl -i --max-time <sec> <url>` | status, headers, body | Нет |
| Что реально загружено? | `systemctl cat <unit>` | directives и drop-ins | Нет |

Не начинай с restart: он меняет evidence и может временно скрыть причину.

## 3. systemd: состояние и конфигурация

### Что различать

- `active` — процесс сейчас считается запущенным.
- `enabled` — unit включён в автозапуск.
- `failed` — последний запуск завершился ошибкой.
- `inactive` — процесс сейчас не работает; это не обязательно ошибка.
- `MainPID` — процесс, который systemd считает главным.

### Полезные формулы

| Формула | Вопрос | Типичная ошибка |
|---|---|---|
| `systemctl status <unit> --no-pager -l` | Каков текущий lifecycle? | Считать `active` доказательством HTTP |
| `systemctl show <unit> -p MainPID -p User -p Group` | Кто и от чьего имени работает? | Смотреть только имя процесса |
| `systemctl cat <unit>` | Какой unit и drop-ins загружены? | Читать только основной файл |
| `systemctl list-units --type=service --all` | Есть ли похожий unit? | Путать unit file и живой process |
| `systemctl status <PID>` | Какой unit владеет PID? | Убивать PID до идентификации |

### Когда нужен daemon-reload

`daemon-reload` нужен после изменения unit-файла или drop-in. Изменение файла,
который приложение читает при старте (`EnvironmentFile`), обычно требует restart
процесса, но не перечитывания unit-структуры.

```text
unit/drop-in изменён -> daemon-reload -> restart
env/app config изменён -> restart
только диагностика -> ничего не перезапускать
```

## 4. Journal и ошибки

Читай ошибку снизу вверх до первой конкретики: errno, путь, адрес, порт или имя
dependency. Traceback важен не целиком, а в месте первого системного отказа.

| Сообщение | Обычно означает | Следующая read-only проверка |
|---|---|---|
| `Permission denied` | Нет нужного `r`, `w` или `x` | identity + `namei -l` + `test` |
| `Address already in use` | Другой socket уже владеет адресом | `ss` по точному порту |
| `Connection refused` | На destination никто не слушает | listener и target URL |
| `Connection timed out` | Пакет/ответ теряется по пути | route, firewall, remote listener |
| `No space left on device` | Закончились blocks или inodes | `df -h` и `df -i` |
| `status=2` / invalid argument | Неверный аргумент или config | полная строка ошибки + config source |

## 5. Process, socket и HTTP

Три уровня нельзя смешивать:

| Уровень | Что он доказывает | Чем проверить |
|---|---|---|
| Process | Код запущен | systemd `MainPID`, `ps` |
| Socket | Процесс принимает соединения на address:port | `ss -lntp` |
| HTTP | Приложение выполнило протокол и контракт | `curl -i` |

Bind-address определяет, через какие интерфейсы доступен listener:

- `127.0.0.1` — только внутри этой машины;
- конкретный IP — только через соответствующий интерфейс;
- `0.0.0.0` — все IPv4-интерфейсы, но firewall всё ещё может блокировать путь.

`curl` доказывает доступность только из точки, где запущен. Локальный успешный
запрос не гарантирует доступ с Mac, балансировщика или другой VM.

## 6. Права и путь

### Числа chmod

```text
r = 4, w = 2, x = 1
owner | group | others
750 = rwx r-x ---
640 = rw- r-- ---
770 = rwx rwx ---
```

Для каталога:

- `r` — увидеть список имён;
- `w` — создавать и удалять записи;
- `x` — пройти через каталог и обратиться к объекту внутри.

Для создания файла нужны `w+x` на каталоге назначения. Проверяй весь путь:

| Формула | Вопрос | State change |
|---|---|---|
| `namei -l <path>` | Где на пути потеряны права? | Нет |
| `ls -ld <dir>` | Кому принадлежит сам каталог? | Нет |
| `ls -l <file>` | Кому принадлежит файл? | Нет |
| `sudo -u <user> test -w <dir>; echo $?` | Может ли service user писать? | Нет |
| `id <user>` | В какие группы входит пользователь? | Нет |
| `chown <owner>:<group> <path>` | Сменить владельца или группу | Да |
| `chmod <mode> <path>` | Изменить mode bits | Да |

`chown` и `chmod` не взаимозаменяемы. Избегай `777`: исправляй точный объект и
минимальный набор битов.

## 7. Filesystem: blocks и inodes

Файловая система имеет как минимум два ограниченных ресурса:

| Ресурс | Что расходует | Проверка |
|---|---|---|
| Blocks | Содержимое файлов | `df -h <path>` |
| Inodes | Количество файлов и каталогов | `df -i <path>` |

Ты можешь иметь свободные гигабайты и не суметь создать пустой файл, если
`IFree=0`. При очистке сначала формируй точную выборку и печатай её:

```text
find <root> -xdev -type f -name '<mask>' <age-filter> -print
```

Только после проверки списка добавляется действие удаления. Не применяй широкую
маску и рекурсивное удаление к неизвестному каталогу.

## 8. Dependencies systemd

`After=` задаёт порядок запуска только для units, уже включённых в транзакцию.
Он не означает «запусти dependency».

`Requires=` создаёт обязательную связь: при старте основного unit systemd также
добавляет зависимость. Часто нужны обе директивы:

```ini
[Unit]
Requires=<dependency>.service
After=<dependency>.service
```

После создания drop-in: проверить `systemctl cat`, выполнить `daemon-reload`,
перезапустить и доказать состояние обеих служб.

## 9. Минимальное исправление

Хороший fix:

- меняет только доказанную причину;
- сохраняет принцип минимальных прав;
- управляет процессом через его supervisor;
- не уничтожает исходные evidence;
- имеет понятный rollback;
- проверяется несколькими независимыми сигналами.

Плохие универсальные реакции: `chmod 777`, kill неизвестного PID, restart всех
служб, отключение firewall, рекурсивное удаление и редактирование кода до чтения
журнала.

## 10. Проверка после исправления

Минимальная лестница доказательств:

1. unit находится в ожидаемом состоянии;
2. MainPID существует и соответствует нужному процессу;
3. listener принадлежит этому MainPID;
4. HTTP возвращает нужный status code;
5. payload соответствует контракту;
6. journal текущего PID не содержит новой ошибки;
7. отдельный checker проходит, если он предусмотрен.

Проверяй с той же точки, где был симптом. Для внешней недоступности нужен внешний
клиент; локальный `curl` недостаточен.

## 11. Быстрая карта решений

| Симптом | Не спешить делать | Сначала доказать |
|---|---|---|
| Unit failed | редактировать первый попавшийся config | точную ошибку и source config |
| Active, но curl не работает | перезапускать | address, port, точку клиента |
| Permission denied | ставить `777` | service identity и проблемный компонент пути |
| Port busy | делать `kill -9` | PID → unit → назначение процесса |
| Errno 28 | удалять большие файлы | blocks или inodes закончились |
| Dependency 503 | менять URL | dependency active, socket, HTTP, graph |

## 12. Одностраничный чек-лист

```text

[ ] Посмотрел systemctl status и MainPID.
[ ] Прочитал journal текущего запуска.
[ ] Нашёл User/Group, ExecStart, EnvironmentFile.
[ ] Проверил listener и его PID.
[ ] Сопоставил listener PID с MainPID/unit.
[ ] Проверил HTTP status и payload из нужной точки.
[ ] При filesystem-ошибке проверил path permissions, df -h и df -i.
[ ] Сформулировал одну доказанную root cause.
[ ] Сделал минимальный fix с понятным rollback.
[ ] Повторил всю цепочку и сохранил evidence.
```
